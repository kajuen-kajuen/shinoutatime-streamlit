## 現状

- テスト基盤: pytest + hypothesis(`_commands.md`「テスト(全部)」)。`tests/unit`・`property`・`integration`・`e2e`(`AppTest`)・`fixtures`
- テストの CI は無い。テストは手元のコンテナで流す
- 2026-05 のリファクタ(リポジトリ・サービスが例外を投げる形に統一)のあと、古い前提(`None` を返す、`get_last_error()`)のまま残っているテストがある【要確認】

## 守るべきものの優先順位

1. データの読み込みと結合 — TSV のヘッダー・配信日の書式(時刻付きを含む)・文字コード、`LIVE_ID` での結合で行が落ちないこと、壊れたファイルで例外(`DataLoadError`)になること
2. 表示用の加工 — No. の番号付け(同じ日に複数配信があるときの `1-3` 形式)、配信日の表示形式、YouTube のタイムスタンプ付き URL
3. 検索 — 大文字小文字・部分一致・配信タイトルを含めるかどうか・空の検索語
4. 楽曲一覧の生成(`song_list_generator`)— 最新の歌唱の選び方、アーティストの読み、類似曲の検出
5. ページ — 各ページが例外なく起動すること、データが読めないときにエラー表示で止まること(e2e)

## 制約

- テストの期待値は仕様(`_common-context.md`・`docs/specs/`)を根拠にする。今の実装の出力をそのまま期待値にしない
- テストのために本番コードを変えるときは、振る舞いを変えない最小のリファクタリングに留める
- テストの依存を新しく足さない(足したくなったら聞く)。ネットワークに出るテストを書かない(モックで)
- `data/` の本物の TSV を書き換えるテストを書かない。書き込みは `tmp_path` に

## 止まって聞く所

1. 対象がテスト可能な形になっていないとき(ページのトップレベルに処理が書かれているなど)。最小のリファクタリング案を出して承認を待つ
2. **テストケース一覧を出したあと**。承認を待ってから実装する

## 決めてよいこと・聞くこと

| 決めてよい | 聞く |
|---|---|
| テストの命名・配置(既存の `tests/` の並びに合わせる) | 本番コードの変更(最小のリファクタリングでも) |
| 境界値・異常系の追加、`tests/fixtures/` への小さなデータの追加 | 期待値が仕様書に無いとき(【要確認】にする) |
| 古い前提のテストを、今の仕様(例外を投げる)に合わせて直す | テストを消す・スキップする |

## 手順

1. 仕様(データ形式・エラー処理の方針・表示の決まり)をテストの期待値の根拠として整理する。完了条件: 対象ごとに根拠の仕様書の節
2. 対象ロジックがテスト可能な形になっているか確認する。テスト不能なら【止まる】最小のリファクタリング案を提示
3. 優先順位の高いものから、正常系・境界値・異常系のテストケース一覧を提示する
4. 【止まる】一覧の承認を待つ
5. テストを実装する。完了条件: `_commands.md`「テスト(全部)」で全件パス
6. 仕様書のテストの節に足し、テスト規約(`_common-context.md`)に追記が要るなら案を出す

## 出力形式

- テストケース一覧表(対象/ケース/期待値/種別(unit・property・integration・e2e)/根拠の仕様書の節) → 実装 → 実行結果(実際の出力)
- カバーできなかったリスクと、ブラウザで確認すべき項目のチェックリスト
