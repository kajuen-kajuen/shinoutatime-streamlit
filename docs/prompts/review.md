## 前提

- 個人運営の公開サイト(Streamlit Community Cloud、無料枠)。利用者の多くはスマホ。リポジトリも公開している
- 最優先ゴールは「正しいデータを、壊れずに、スマホでも探しやすく表示し続けること」と「公開リポジトリから秘密や個人情報を漏らさないこと」
- コードの修正は行わない。レビューと提案、記録まで

## レビュー観点(優先度順)

1. 公開リポジトリとしての安全(秘密の値・個人情報・ローカルの絶対パス、管理ページの扱い、既定のパスワード)
2. データの正しさ(TSV の件数・形式の変化、結合で行が落ちる、番号付け・日付・URL の誤り)
3. 障害時の振る舞い(例外がページまで来て落ちる、キャッシュ関数の中の表示、分かりにくいエラー表示)
4. 表示の安全と使いやすさ(エスケープしない HTML、スマホの幅、検索・絞り込みの分かりやすさ、アクセシビリティ)
5. 保守性(ページ間の重複、使われていないコード、テストの穴、依存の版の固定)
6. 性能(全件を毎回加工している、キャッシュの効き方)

## 止まって聞く所

1. **指摘の一覧を出したあと**。直す・見送るの判断はユーザーが行う。指摘を勝手に直さない
2. 記録(`docs/reviews/`)を書く前に、記録の対象(コミットの範囲)と種別を確認する

## 決めてよいこと・聞くこと

| 決めてよい | 聞く |
|---|---|
| 指摘の重要度の付け方(下の目安で) | 指摘への対応(直す・見送る) |
| 記録のファイル名(`docs/reviews/<日付>-<対象>.md`) | 前回の記録の状態(対応済みなど)を変えること |

## 手順

1. プロジェクト構造を把握し、主要ファイル(`Home.py`・`pages/`・`src/ui/pages/home_page.py`・`src/repositories/`・`src/services/`・`src/core/data_pipeline.py`、v2 の `src/models/schema.py`・`src/repositories/table_repository.py`・`src/core/views.py`・`src/core/validation.py`・`src/ingest/`・`src/cli/ingest.py`・`src/cli/data.py`)を精読する。構成の概要は `docs/architecture/overview.md`。完了条件: 各ファイルの責務を1行で言える
2. `sh tools/check-rules.sh` と `_commands.md`「テスト(全部)」を流し、チェックリストの表を埋める
3. 観点ごとに問題を洗い出す。推測ではなく必ず該当コードを確認してから指摘する。完了条件: 各指摘に「ファイル:行番号」「問題の内容」「利用者・運用への影響」「修正案の概要」
4. 【止まる】総評・指摘一覧・Top 5 を出し、対応の判断を待つ
5. 記録する: `docs/reviews/_template.md` をコピーして `docs/reviews/<YYYY-MM-DD>-<対象>.md` を書く(範囲と観点・指摘の表・結論。「レビューした人」は Claude と、使ったモデル)。`docs/README.md` の「レビュー記録」の表に1行足す。完了条件: 2ファイルの差分

## 出力形式

- 総評(3行以内)
- 絶対制約のチェックリストの表
- 指摘一覧: 重要度(高/中/低)順の表(# / 重要度 / 場所 / 内容 / 影響 / 修正案)。高=秘密・個人情報の漏えい、データの欠落・誤表示、ページが落ちる
- 「次にやるべきこと Top 5」を根拠付きで提案

## 終わりの型

記録の2ファイル(`docs/reviews/…` と `docs/README.md`)の差分の要約 → 【要確認】【仮定】の一覧。コードは変えていないので、`check-rules.sh` とテストは記録の前に流した結果を書く。
