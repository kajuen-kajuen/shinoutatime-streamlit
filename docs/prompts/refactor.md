## 絶対条件

- 外部から見た振る舞い(表示する行と並び順、件数、No. の番号付け、YouTube のリンク先、検索の結果、エラー時の表示)を1ミリも変えない
- `docs/prompts/_common-context.md` の設計ルールを維持する。特に:
  - 層(repositories → services → core → ui)と、失敗は例外で上げる方針
  - 読み込みは `@st.cache_data` の関数で、その中で表示しない
  - データ由来の文字列をエスケープせずに HTML に埋め込まない
- `data/` の TSV の形式・列は変えない(`data/v2/` も同じ。列と値の形は `src/models/schema.py` と `docs/specs/data-model.md` が正本)。変えたくなったら、それはリファクタリングではなく feature として別に扱う
- 公開している関数・クラスの名前を変えるときは、`tests/` と `src/cli/` からの呼び出しもすべて追う。v2 の部品(`src/core/views.py`・`src/ingest/`・`src/repositories/table_repository.py`)は、画面(`src/ui/v2_data.py`・`home_page.py`・`pages/99_Song_List_beta.py`)と CLI(`ingest`・`data`)から呼ばれる
- `views.py` の集計を変えるときは、性能テスト(`pytest --runslow`)も流す。`lambda` での集計や Arrow の文字列のままの min・max は、2万件で遅くなる(`docs/specs/data-model.md` の4章)

## 止まって聞く所

1. 対象の責務・依存関係の図解を出したあと(私の認識と合っているかの確認)
2. **移行計画を出したあと(Plan Mode)**。承認を待ってから着手する
3. あるステップでテストが落ちるとき(先に進まず報告する)

## 決めてよいこと・聞くこと

`_common-context.md` の表のとおり。この作業で特に:

| 決めてよい | 聞く |
|---|---|
| 承認された計画の中でのファイル名・関数名 | 計画に無いファイルへ手を広げること |
| 等価性を固定するためのテストの追加 | 振る舞いが変わるかもしれないと気づいたとき(変えずに止まる) |

## 手順

1. 対象コードの現状の責務・依存関係を図解(テキスト)する。【止まる】私の認識と合っているか確認
2. 移行計画を「各ステップ後もテストが通り動作する」小さい単位に分割して提示する。先に等価性を固定するテスト(今の出力ではなく仕様を根拠に)が要るかも書く
3. 【止まる】Plan Mode で承認を待つ
4. 承認後、1ステップずつ実施する。完了条件: 各ステップで `_commands.md`「テスト(一部)」が通る
5. 全ステップ完了後、`sh tools/check-rules.sh` と `_commands.md`「テスト(全部)」を通し、ブラウザで確認すべき操作のチェックリストを出す

## 出力形式

- Plan Mode: Before/After 構造図 → ステップ一覧(各ステップの変更ファイルとリスク) → 「等価性の根拠」セクション
- 実装後: ステップごとの差分要約。壊れた場合に切り戻しやすい単位で報告

## 終わりの型

`sh tools/check-rules.sh` → `_commands.md` のテスト → ステップごとの差分の要約 → 【要確認】【仮定】の一覧。
