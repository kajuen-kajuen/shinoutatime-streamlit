## 調査の当たり(このアプリで問題が起きやすい箇所)

- TSV の形式の変化: ヘッダー名、配信日の書式(`YYYY/M/D` と `YYYY/M/D HH:MM`)、URL の形(`watch?v=`・`/live/`・`youtu.be/`)、文字コード
- 配信と歌唱の結合: `LIVE_ID` の不一致で行が落ちる、件数が合わない
- YouTube のタイムスタンプ付き URL の生成(`src/core/utils.py` の `generate_youtube_url`。`?` と `&` の付け方)
- 例外の扱い: リポジトリ・サービスが投げた例外をページが捕まえていない、捕まえる側が古い戻り値(`None`)を前提にしている
- キャッシュ: `@st.cache_data` の TTL のせいで古いデータが出る、キャッシュ関数の中の表示が出ない
- `st.session_state` に古い検索結果が残る
- Streamlit の版の違い(ローカルと Streamlit Cloud)、内部クラス名に依存した CSS
- `data/` の更新で件数が大きく変わった(`_commands.md`「データ件数の確認」「本番のデータ件数」)

## 制約

- 仕様上意図的な挙動(`docs/specs/` の決定事項)をバグと誤認しない
- 修正は最小にし、絶対制約(main・develop に触れない、秘密を入れない、データを確認なしで書き換えない、エスケープしない HTML を足さない、キャッシュ関数の中で表示しない)を崩さない
- データが原因のときは、データを直さずに報告して止まる(データの修正はユーザーが判断する)

## 止まって聞く所

1. 発生条件が足りないとき(調査の前)
2. **原因を確定したあと、修正コードを書く前**。原因と最小の修正案を出して返事を待つ。データ・依存・キャッシュの設定に触る修正は、必ずここで承認を取る

## 手順

1. 仕様上意図的な挙動を、`_common-context.md` と `docs/specs/` で確かめる。完了条件: 症状が「仕様どおり」でないと言える
2. 症状から仮説を最大3つ立て、それぞれ「何を見れば白黒つくか」を宣言する。完了条件: 3つ以下の仮説と、確かめ方の表
3. コードリーディング(必要ならログ追加・`_commands.md`「アプリのログ」)で仮説を検証する。推測で修正しない。完了条件: 原因箇所を「ファイル:行番号」で指せる
4. 【止まる】原因と最小の修正案を提示し、承認を待つ
5. 修正し、再発を防ぐテストを足す。完了条件: `sh tools/check-rules.sh` が問題なし、`_commands.md`「テスト(全部)」が通る
6. 再発防止(`_common-context.md` や仕様書への追記)が必要か判断して提案する

## 出力形式

- 原因: 「ファイル:行番号」+ 因果関係の説明(なぜこのコードがこの症状を生むか)
- 修正: 差分要約と、修正が副作用を生まない根拠
- 検証手順: 私がブラウザで確認すべき操作(ページ・入力・期待する表示)
